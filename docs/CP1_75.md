# CP1.75 — Realistic service behavior for incident detection

**Scope:** A focused increase in example-app complexity before CP2 evidence tools.
No LLM, cloud integration, OpenTelemetry backend, alert rules or remediation is added.

## Why this matters

Earlier cases mainly surfaced an obvious 5xx or a single fixed delay. A more realistic
detector must identify **masked failures**: a dependency can degrade while customers
still see success because the application retries.

The new verification path performs actual work:

1. Read the order from PostgreSQL.
2. Call the local HTTP provider and propagate the request ID.
3. Retry a transient 503 or request error **once**, after 100 ms.
4. Emit an observation for each attempt and the overall API request.
5. Return 200 on eventual success or 502 after both provider attempts fail.

The database readiness probe remains healthy in both newly injected scenarios.
A diagnosis based only on the database or outer HTTP status is insufficient.

## Two new scenarios

**Transient provider degradation:** `make fault-provider-flaky` causes the first
provider attempt to return 503 after about 180 ms. The second attempt succeeds.
The client receives HTTP 200, but dependency failure and retry counters increase.

**Sustained provider outage:** `make fault-provider-outage` causes both attempts
to return 503. The client receives HTTP 502 while PostgreSQL readiness stays 200.

## Investigator-visible signals

| Source | Observable | Purpose |
|---|---|---|
| API log | `request_completed` | Outer request status and duration |
| API log | `dependency_request_completed` | Provider attempt, result and duration |
| API log | `upstream_retry_scheduled` | Retry overhead, transient masking |
| API log | `upstream_request_failed` | Final provider-level failure |
| Provider log | `provider_request_completed` | Match service events by safe request ID |
| `/metrics` | `traceops_dependency_attempts_total` | Detect hidden dependency errors |
| `/metrics` | `traceops_dependency_retries_total` | Count retry amplification |
| `/metrics` | `traceops_dependency_duration_seconds` | Attempt-level latency histogram |
| `/metrics` | HTTP status and duration series | Compare dependency issues with user impact |
| `/health/ready` | PostgreSQL readiness | Counterexample to a health-only detector |

Telemetry has bounded labels and omits request bodies, raw URLs, identifiers, secrets
and exception messages. The evidence exporter matches provider events to current API
request IDs, avoiding old provider events in later scenarios. New evidence JSON files
omit scenario labels in their payload; **filenames are still evaluator metadata**.

## Experiment

```bash
make up
make reset && make traffic
make fault-provider-flaky && make traffic
make fault-provider-outage && make traffic
make reset
make integration
```

Each traffic run reports status counts and p50/p95 latency. Those are useful
observations, not a measured model benchmark. `make integration` also captures
sanitized evidence and verifies expected statuses for the new cases.
