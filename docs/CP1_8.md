# CP1.8 — Reproducible incident timeline replay

**Goal:** Produce a believable time-dependent incident for a detector and agent
to investigate without handing them the injected root cause.

**Status:** On PR #9. GitHub CI and independent local verification must establish
the passing state before this checkpoint is considered complete.

## Architecture

```text
continuous request traffic -> NestJS API -> PostgreSQL
                                     |
                                     +-> mock HTTP verification provider

host replay scheduler -> local fault.json -> mock provider (read per request)
                        |-> timestamped metrics snapshots
                        |-> correlated safe logs
                        |-> agent evidence + separate evaluator metadata
```

- NestJS stays running throughout, so in-process counters preserve incident history.
- A local-only atomic JSON file changes **only the provider's behavior**.
- The provider reads the file for every request. No public fault endpoint exists.
- The runner sends bounded traffic and samples `/metrics` approximately once per second.
- Safe request IDs link API logs, provider logs and traffic results.
- A synthetic **deployment_completed** change-feed event occurs near the start
  of degradation. It is *non-causal*, testing whether an agent can distinguish
  correlation from a verified explanation.

## Five replay windows

| Window | Provider behavior | Typical API result | Relevant signal |
|---|---|---|---|
| Baseline | Healthy | 200 | Baseline |
| Latency rise | +180 ms provider delay | 200 | Increased p50/p95 |
| Retry masking | First call 503 then retry 200 | 200, slower | Hidden dependency failures |
| Provider outage | Every call 503 | 502 | Customer-facing incident |
| Recovery | Healthy again | 200 | Restored success |

This is a controlled teaching scenario, not yet a complex production benchmark.

## Run

```bash
make up
make reset
make replay        # five 6-second windows, 4 req/sec default
make replay-check  # five 3-second windows, 5 req/sec with assertions
curl http://localhost:3000/metrics
make down
```

The Python runner accepts loopback HTTP origins only and caps phases at
2–30 seconds and traffic at 1–8 requests/sec. It uses no cloud services.

## Agent/evaluator boundary

**Agent-visible file:** `artifacts/evidence/replay-<id>.json`

Contains timestamped HTTP status/latency, Prometheus-style metric samples,
sanitized correlated two-service events, and one simulated change-feed marker.
It does not contain the injected modes, phase labels or root cause.

**Private evaluator file:** `artifacts/private-ground-truth/replay-<id>.json`

Contains the exact injected schedule, time boundaries, causal component and
the non-causal release marker. This path is Git-ignored; CI does not upload it.
Never expose it to the future investigator through a tool or prompt.

The CI validation script may read both files; production agent tools must not.

## Exit gates

- [x] Provider behavior changes without a NestJS restart
- [x] Continuous traffic spans five successive time windows
- [x] Request IDs correlate records across API and provider
- [x] Per-second snapshots preserve metrics before and after failure
- [x] Deployment event is a documented non-causal distractor
- [x] Ground-truth modes and schedules are stored separately from public evidence
- [x] Automated correctness, privacy and artifact validation checks added
- [ ] GitHub replay CI passes
- [ ] Clean-machine Docker Compose run passes outside GitHub CI

## Not built yet

This is not OpenTelemetry distributed tracing: there is no collector, span graph,
CloudWatch adapter, autonomous detection agent or LLM yet. CP2 should provide
**read-only time-window evidence tools** over these observations; then a deterministic
detection baseline can locate onset and recovery before the agent tries to explain them.
